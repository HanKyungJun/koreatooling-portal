# 검토 역할 자동 지정 (review-role)

「검토해 줘」라고만 해도 대상에 맞는 전문가 역할을 정하고, 그 역할의 검토표대로 본다.
역할은 말투가 아니라 **어떤 검토표를 적용하느냐**다.
경준님은 스킬 이름을 외우지 않는다 — 「검수해 줘」 한마디면 필요한 스킬 조합(코드면 code-review, 파이썬이면 python-review 까지)은 이 스킬이 알아서 부른다(2026-11-11 요청 · 2026-11-20 python-review 추가).

## 0. 원본 규칙 — 먼저 읽는다

- 역할 R1~R5 검토표와 판정 규칙의 원본은 `wiki/standards/AI-역할-검토표.md` 다. 검토 시작 전에 반드시 읽고, 이 스킬에 옮겨 적지 않는다(두 곳 관리 금지).
- 이 스킬이 하는 일은 ① 역할 고르기 ② 코드면 code-review 연결(§1-A) ③ 표에 없는 대상용 보조 검토표(R6 · R7) ④ 결과 형식, 네 가지뿐이다.
- R6 · R7 은 **제안 역할**이다. 한경준님 승인 후 원본 표에 옮기고, 그때 이 스킬의 해당 절을 지운다.
  - 스킬 저장(2026-11-10)은 이 스킬을 쓰는 것에 대한 승인이다. 원본 표 반영은 원본 표 §4 측정 기간(2026-12-03까지) 동안 시험 운영한 뒤 따로 승인받는다.
- **원본을 못 읽는 환경**(챗 · 휴대폰 · PC 연결 끊김)에서는 이 스킬의 §1 · §3 만으로 진행하고, 검토 줄 끝에 `· 원본 표 미확인` 을 붙인다.
- **전용 스킬이 먼저다** — 위키 검수 · lint → `wiki-lint`, 일일보고서 누락 → `daily-report-check`, 자동화 누락 원인 → `scheduler-diagnose`, Vc ↔ RPM 계산 → `grinding-calc`. 이 스킬은 그 결과에 역할 판정과 검토 줄만 덧붙인다.
- **작은 일은 공통 G1 만** 본다(CLAUDE.md §16 · §15-1) — 문장 하나 · 화면 문구 · 되돌리기 쉬운 수정. 역할 표 · 엑셀 검수표 · 스크린샷은 쓰지 않고 검토 줄은 `검토(G1): 통과 1` 처럼 한 줄.

## 1. 역할 고르기

| 검토 대상 | 주 역할 | 같이 볼 역할 |
|---|---|---|
| 연삭 · 가공 조건, G-code, 휠 스택 | R1 가공 · 연삭 공정 | R3 (실측이 있으면) |
| 공구 도면 · 형상 · ToolRoom | R2 공구 설계 | R1 |
| 테스트 기록 · 측정값 · 불량 원인 | R3 품질 · 측정 | R1 |
| 스크립트 · 프로그램 · ERP 데이터 · 예약 작업 · git | R4 자동화 · 데이터 | 코드면 code-review (§1-A) |
| 보고서 · 계획서 · 발표자료 · 정가표 · 대외 문서 | R5 보고서 · 대외 문서 | 숫자가 있으면 R4 |
| 웹사이트 · 쇼핑몰 · 랜딩 페이지 · 웹 폼 · 화면 디자인(배치 · 색 · 글자) | R6 웹 · 쇼핑몰 QA (제안) — 디자인이면 R6-A 까지 | 가격이 있으면 R4 · R5, 약관이 있으면 R7 |
| 약관 · 계약서 · 개인정보처리방침 · 견적 조건 | R7 계약 · 정책 문서 (제안) | R5 |
| AI 지침 · 스킬 · 예약 작업 프롬프트 · CLAUDE.md | R4 자동화 · 데이터 | R5 (문장) |
| 대외 메일 · 메시지 초안 | R5 보고서 · 대외 문서 | 약속 · 조건이 있으면 R7 |

- R1~R5 행은 CLAUDE.md §16 표를 풀어 쓴 것이다. 어긋나면 §16 이 우선이고, §16 이 바뀌면 이 표도 같이 고친다.

- 대상이 둘 이상에 걸치면 주 역할 1개 + 걸리는 역할을 **모두** 적용한다.
- 대상이 모호하면(파일 · URL · 범위 없음) 묻기 전에 먼저 열어 보고, 그래도 모호하면 추천안 1개 + 이유를 붙여 승인만 받는다.
- 「봐줘」「어때?」만 있어 검토인지 설명 요청인지 애매하면, 검토표를 돌리지 말고 먼저 내용을 답한 뒤 검토가 필요한지 한 줄로 묻는다.
- 범위가 크면(예: 품목 수만 건) 범위 · 판정 기준 · 결과 형식을 추천안으로 먼저 확정한다.

### 1-A. 대상이 프로그램(코드)이면 — code-review 자동 연결

R4 검토표는 운영 실수(단정 · 안내 상자 · git · 예약 작업 · ERP)를 막는 항목이라 코드 자체의 버그 · 속도 · 오류 처리는 보지 않는다. 그래서 대상이 코드면 사용자가 따로 말하지 않아도 아래 순서로 한다.

1. 대상 판정 — `.py` · `.ps1` · `.bat` · `.js` · `.gs`(Apps Script) · 스크립트가 든 `.html`, 또는 「프로그램 · 코드 · 스크립트 · 뷰어 · 창 프로그램」 검수 요청.
2. `engineering:code-review` 스킬을 Skill 도구로 불러 코드 자체를 본다 — 정확성 · 오류 처리 · 성능(느림 · 버벅임) · 스레드 · 동시 실행 · 보안(토큰 · 비밀번호 하드코딩).
   - 범위: 바뀐 부분이 있으면 그 부분 + 그것을 부르는 곳, 없으면 주 실행 경로. 범위를 결과에 적는다.
   - 실제로 돌려 볼 수 있으면 돌려 본다(실행 · 문법 검사). 못 돌린 지적은 「확인 필요」.
   - **대상이 `.py` 면 `python-review` 스킬도 Skill 도구로 불러** 파이썬 고유 항목(P1~P9)과 사내 실행 환경 항목(W1~W8 — 인코딩 · 작업 스케줄러 · exe · 엑셀 · 삭제 · KST · 종료 코드 · PC 경로)을 본다(2026-11-20 추가). 같은 줄을 code-review 와 두 번 지적하지 않는다.
3. 이어서 R4 + 공통 G1~G6 를 적용한다(원본 표).
4. 결과를 **표 하나**로 합친다 — 「구분」 열에 `코드`(code-review) / `Py`(python-review) / `R4` / `G` 로 출처를 적는다. 검토 줄 예: `검토(R4 주 · 코드 리뷰 · Py): 통과 n · 확인 필요 m(대표 항목)`
5. code-review 스킬을 못 부르는 환경이면 2의 항목을 직접 보고 검토 줄 끝에 `· code-review 미사용` 을 붙인다. python-review 를 못 부르면 `· python-review 미사용`.

- 검수는 지적과 수정안까지다. 코드를 고치는 것은 경준님 「진행」 뒤.
- 한두 줄 수정 · 문구만 바뀐 코드는 §0 「작은 일」로 보고 G1 + 문법 검사만 한다(code-review 생략, 검토 줄 `검토(G1): 통과 n`).
- 대상 없이 「검수해 줘」만 오면 직전에 만들거나 고친 산출물을 대상으로 잡고, 답 첫 줄에 무엇을 대상으로 잡았는지 적는다.

## 2. 보조 검토표 (원본 표에 없는 대상)

### R6 웹 · 쇼핑몰 QA (제안)

| # | 확인 | 증거 예 |
|---|---|---|
| R6-1 | 공개 페이지에 내부 메모 · 초안 문구 · 파일명 · 담당자 지시가 없는가 (약관 · 개인정보 · 공지 포함) | 해당 문구와 URL, 스크린샷 |
| R6-2 | 같은 사실(배송비 · 출고일 · 환불 · 품목 수 · 연락처)이 페이지마다 같은가 | 페이지 쌍과 두 값 |
| R6-3 | 부가세 포함가 계산 규칙(반올림 · 올림 · 버림)을 먼저 확인하고 전 품목이 같은 규칙인가, 가격 누락 · 0원 | 전수 검사 건수 |
| R6-4 | 같은 계열 안의 가격 역전 · 튀는 값(중앙값 대비 1.6배 초과 · 0.6배 미만 — 2026-11-10 1회 쓴 사내 경험값, 계열 특성에 맞게 조정) · 원 단위 정가 | 품번 · 값 · 비교 기준 |
| R6-5 | 같은 품번 중복 등록, 품명 = 품번, 비상품(비용 · 수수료 코드) 노출 | 건수와 예시 |
| R6-6 | 오타 · 외래어 표기 · 한영 혼용 · 영문 철자 | 현재 표기 → 수정안 |
| R6-7 | 오탐 반증 — 의심 항목은 같은 계열 건수를 한 번 더 찾아보고, 일관된 계열이면 제외 | 제외 사유 |
| R6-8 | 지적마다 스크린샷(지적 위치 강조) — 화면 강조만, 사이트 변경 없음 | 파일명 |

- 수집은 사용자 브라우저에서 사람이 쓰는 속도를 넘지 않게 한다. 대량 페이지는 표본으로 바꾸고 표본 범위를 결과에 적는다.
- 가격의 정답은 사이트 안에 없다. 사이트 안 비교로 걸린 것은 「확인 필요」, ERP · 정가표와 대조된 것만 「통과 / 오류」.

#### R6-A. 화면 다듬기 — 디자인을 볼 때 (2026-11-25 추가)

「디자인 · 배치 · 보기 좋게」를 검토하거나, 웹 화면을 새로 만들었거나 크게 고쳤을 때 R6-1 ~ 8 에 더해 본다. 순서는 oil-ui(github.com/oil-oil/oil-ui, MIT) 「기존 화면 다듬기 검토」를 사내에 맞춘 것이다.

| # | 확인 | 증거 예 |
|---|---|---|
| R6-9 | 규격 이탈 — 그 화면의 공통 CSS · 디자인 시스템(코고툴 디자인 시스템 · portal.css 등)에 없는 색 · 글자 크기 · 모서리, 공통 부품이 있는데 따로 만든 것 | 위치 · 쓰인 값 · 규격 값 |
| R6-10 | 배치 — 규격 안에서 완성도를 가장 해치는 **세 곳만**(위계 · 정렬 · 여백 · 글 잘림 · 끝선 어긋남) | PC 1440 px · 휴대폰 390 px 스크린샷 + 잰 값(px) |
| R6-11 | 읽힘 — 글자 대비(본문 4.5 : 1 미만), 핵심 입력 · 내용이 휴대폰 첫 화면 밖에서 시작 | 대비값 · 시작 위치(px) |
| R6-12 | 움직임 — 바뀐 부분의 움직임 효과가 빠지거나 깨졌는가(없으면 해당 없음) | 확인한 동작 |
| R6-13 | 뺄 것 — 같은 제목 두 번 · 꾸밈 그림 글자 · 없어도 되는 설명 문단 | 목록 |

- 증거는 실제 화면에서 낸다 — 파일이면 작업 공간에서 Playwright 로 PC · 휴대폰 두 크기 스크린샷과 `getBoundingClientRect` · `getComputedStyle` 측정, 공개 사이트면 브라우저. 못 본 화면은 「실제 화면 미확인」. 점수는 매기지 않는다.
- 브랜드 색 · 글꼴 · 큰 틀을 바꾸자는 제안은 하지 않는다. 새 시안도 내지 않는다(검토만 — 시안 비교는 코고툴 디자인 시스템 「화면 배치」 방식으로 따로).
- 만든 쪽(같은 대화의 Claude)이 직접 본 검토는 결과 첫머리에 「독립 검토 아님」을 적는다.
- 창 프로그램(ERP 뷰어 등)은 경준님 PC 스크린샷이 있을 때만 R6-9 · R6-10 · R6-13 을 적용한다.

## 3. 판정과 결과 형식

- 판정은 셋 — **통과**(증거 필수) / **확인 필요** / **해당 없음**. 증거 없는 통과 금지.
- 지적은 표로: 심각도(상 · 중 · 하) · 구분 · 위치 · 현재 표기 · 문제 · 수정안 · 상태(실물 확인 / 확인 필요).
- 심각도 기준: 상 = 고객 · 금전 · 법적 영향 또는 내부 정보 노출 / 중 = 수치 · 정책 불일치, 가격 패턴 이상 / 하 = 표기 혼용.
- 지적이 10건을 넘으면(사내 경험값) 엑셀 검수표(요약 · 검수표 · 검사 범위 · 스크린샷 시트)로 낸다.
- 저장 위치: 실거래 단가 · 할인율 · 견적 금액이 들면 `wiki/_private/`(CLAUDE.md §4). 공표 정가만 든 검수표 · 스크린샷은 대외비가 아니지만(§4-1) 직원 연락처 등이 섞이므로 `outputs/`(git 추적 제외 — 저장 전 `git check-ignore` 로 확인)에 둔다.
- 답 끝 한 줄(원본 표 §0-3): `검토(R6 주 · R4 · R7): 통과 n · 확인 필요 m(대표 항목)`
- 검토 줄 다음에 CLAUDE.md §0-D **결론 블록**(현황 · 다음 작업 — 경준님 / Claude / 대기 · 승인 요청)을 둔다. 문단형 결론으로 대신하지 않는다(2026-11-20 테스트카드 #8 ① 기록).
- 대외 발송 · 정가 · 양산 조건 · 보고서 제출용 최종본은 원본 표 §0-4 대로 별도 검토를 제안한다.

## 4. 하지 않는 것

- 역할을 정했다고 말투를 바꾸지 않는다. 바뀌는 것은 검토표다.
- 현장 전문가 판정을 대신하지 않는다 — 안전 · 설비 · 가격 확정은 담당자 최종 확인.
- 맞는 값을 지어내지 않는다. 모르면 「확인 필요」.
